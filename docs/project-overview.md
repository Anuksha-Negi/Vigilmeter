# VigilMeter
### QR-Based Authenticated Electricity Monitoring & Billing System
**BTech Major Project — Software Perspective Documentation**

---

## 1. Project Overview

**VigilMeter** is a QR-code based, officer-authenticated electricity monitoring and billing system designed to prevent electricity theft and unauthorized meter tampering. Each household meter is tagged with a unique, encrypted QR code linked to a smart monitoring chip that records real-time voltage/current fluctuation data with timestamps. Only authenticated government officers can scan the QR code to access house-specific consumption and fluctuation data, generate bills, and log their site visit — creating a transparent, tamper-proof audit trail. The system automatically applies escalating penalties based on recorded fluctuation data, ensuring accountability on both the consumer and the officer side while eliminating manual/remote billing fraud.

**One-line summary:** A tamper-proof, QR-authenticated system that links smart meter fluctuation data to officer-verified billing, automatically penalizing electricity theft.

---

## 2. Problem Statement

| Problem | Description |
|---|---|
| Rampant power theft | Meter tampering and illegal hooking cause massive revenue losses for electricity boards. |
| No officer accountability | No verifiable record of which officer visited which house, or whether a reading was genuinely checked on-site. |
| Manipulable remote billing | Online/remote billing can be manipulated without physical, location-verified confirmation of actual usage. |

---

## 3. Objectives

1. Uniquely identify every household meter using an encrypted QR code.
2. Allow **only authenticated government officers** to access house-specific billing/fluctuation data.
3. Maintain a complete, tamper-proof **audit trail** of every officer visit.
4. Automatically calculate bills using consumption + fluctuation (tampering) data.
5. Apply an **escalating penalty system** for repeated tampering, ending in an official notice.
6. Provide a central government dashboard for analytics and oversight.

## 4. Project Scope

To keep the project realistic and achievable within 6 months as a software-focused BTech project, the scope is split clearly:

### In Scope — Software Layer (fully built by this project)
- QR generation & encrypted scan handling
- Officer authentication (JWT + Role-Based Access Control)
- Bill generation & escalating penalty engine
- Officer visit logging & audit dashboard
- Government analytics dashboard
- A **simulation layer** that emulates real-time chip fluctuation data

### Assumed / Simulated — Hardware Layer (future scope, not built now)
- IoT chip voltage/current fluctuation sensing (ESP32 + ZMPT101B + ACS712)
- Real-time physical meter readings
- Physical tamper sensors

> The hardware chip's data feed is treated as a **given input** — for the prototype it is generated by a realistic simulation script, so the software system can be fully built, tested, and demonstrated without waiting on hardware.

## 5. System Architecture
- **Meter + QR**: Each physical meter carries a QR sticker encoding an encrypted house/meter ID. The (simulated) chip continuously feeds fluctuation readings to the backend.
- **Backend API**: Central service handling authentication, QR resolution, billing logic, and logging.
- **Database (PostgreSQL)**: Stores households, officers, meters, bills, fluctuation logs, and visit logs.
- **Officer App**: Mobile app used on-site to scan QR codes and generate bills — only after login.
- **User Portal**: Web dashboard where consumers view their bills, penalty history, and notices.
- **Gov Dashboard**: Central analytics view — tampering trends, officer activity, revenue impact.

## 9. Technical Workflow (End-to-End Data Flow)

The core operational flow, step by step:

1. **Officer Reaches House**
   Officer opens the app on-site; location is optionally captured for verification.

2. **Scans Meter QR**
   The encrypted meter ID (embedded in the QR) is sent to the backend along with the officer's active session token.

3. **Auth Verified**
   Backend confirms the officer's identity, role, and whether the house falls within their assigned area.

4. **Data Fetched**
   Consumption history and fluctuation/tampering logs (from the chip's simulated feed) are pulled for that specific meter ID.

5. **Penalty Logic Applied**
   The fluctuation history is evaluated:
   - No flagged fluctuation → normal bill
   - 1st fluctuation → +25% penalty
   - Repeat fluctuation → penalty doubles the original bill
   - Continued violation → official notice generated

6. **Bill Generated & Locked**
   The bill is generated and **locked only after officer authentication succeeds** — preventing any remote or unauthenticated billing.

7. **Visit Logged**
   The scan event (officer + house + timestamp) is written to the immutable audit trail.

8. **Data Surfaced**
   - The consumer sees the bill and penalty reason on the **User Portal**.
   - The government sees aggregated trends and officer activity on the **Gov Dashboard**.

## 10. Penalty Escalation Logic

| Stage | Trigger | Action |
|---|---|---|
| Normal Usage | No fluctuation flagged | Standard bill |
| 1st Fluctuation | First tampering signature detected | +25% penalty on bill |
| Repeat Fluctuation | Second occurrence | Penalty doubles the original bill |
| Continued Violation | Further repeat | Official notice issued |

> Escalation resets to normal only after a clean review cycle confirms genuine, non-tampered usage.

## 11. Security Measures

- **HMAC-signed fluctuation data packets** with sequence numbers — prevents replay/tampering of chip data in transit.
- **JWT-based authentication** with role-based access control (officers only see their assigned area).
- **bcrypt/argon2** password hashing — never store plain-text passwords.
- **HTTPS** for all API communication.
- **Encrypted sensitive fields** (address, meter ID) in the database.
- **Maker-checker approval** for high-value penalties, to reduce risk of officer misuse.
- **Immutable audit logs** — no deletion, only append-style correction entries.

## 13. Limitations & Future Scope

| Limitation | Planned Fix / Future Scope |
|---|---|
| Fluctuation data is simulated | Integrate a real IoT chip (ESP32 + voltage/current sensors) |
| Threshold-based false positives | ML-based anomaly detection (e.g., Isolation Forest) |
| Officer override risk | Maker-checker approval + automatic escalation alerts |
| QR cloning risk | GPS-bound verification or rotating/dynamic QR codes |
| Offline dependency | Offline-first local cache + background sync queue |
| Scalability untested at city scale | Load testing, Redis caching, database sharding |
| No real hardware validation | Realistic simulation now; real meter calibration in future phase |

---

## 14. Conclusion

VigilMeter ties QR-based officer authentication to fluctuation-aware billing, producing a transparent, tamper-resistant system for both citizens and the electricity board. By scoping the project around the **software layer** — authentication, QR handling, billing logic, audit trails, and analytics — while treating hardware fluctuation data as a simulated, swappable input, the project remains fully achievable, demo-ready, and technically substantial within a 6-month BTech timeline, with a clear and credible path to real IoT integration in the future.
